# 하루치 — 캘린더·할일·타이머 통합 설계

2026-09-02 · Merci(timereci)에서의 피벗

## 무엇을 만드는가

하루를 여는 화면 한 장에 **약속과 할일이 같이 있고, 무엇이든 탭하면 타이머가 도는** 앱.

기존 Merci는 "집중한 만큼 발행되는 감성 영수증"이었다. 영수증이라는 축을 걷어내고,
그 자리에 **캘린더**를 넣는다. 타이머와 할일 목록은 이미 구현돼 있으므로 이번 작업의
무게중심은 캘린더 연동과 Today 화면 재구성이다.

앱 이름은 **하루치**("오늘 하루치 일"), 패키지는 `com.haruchi.today`로 바꾼다.
아직 출시 전이라 기존 설치 데이터를 보존할 의무가 없다.

## 확정된 결정 원장

| # | 결정 | 근거 |
|---|---|---|
| 1 | 캘린더는 **시스템 연동**, 할일은 **자체 구현** | Google Tasks는 OAuth·네트워크·동기화 충돌이 붙는데, 앱에 이미 할일 목록이 있어 얻는 게 적다 |
| 2 | 캘린더 쓰기는 **간단 추가까지만** | 반복 일정 편집("이 회차만 / 앞으로 전부")이 복잡도의 대부분이다. 그건 삼성 캘린더로 넘긴다 |
| 3 | 메인은 **오늘 한 장** — 일정은 땅금, 할일은 목록 | 약속과 할일을 억지로 같은 것으로 만들지 않으면서 한눈에 본다 |
| 4 | 캘린더 일정도 **탭하면 타이머**, 일정 길이가 기본값 | 규칙이 하나여야 익히기 쉽다. 치과 같은 건 안 누르면 그만 |
| 5 | 완주하면 **자동 저장**. 메모·사진은 선택 | 지금은 발행 화면을 반드시 거쳐야 한다. 이게 남은 번거로움의 핵심 |
| 6 | 집중 기록의 캘린더 되돌리기는 **설정에서 켤 때만** | 기본으로 켜면 하루 여러 번 집중할 때 남의 캘린더가 금방 빽빽해진다 |
| 7 | 월간·주간 전체 뷰는 **만들지 않는다** | 삼성 캘린더가 이미 잘 한다. 우리 질문은 "오늘 뭘 언제 하지"다 |
| 8 | DB 엔티티 이름은 **그대로** 둔다 | `ReceiptEntity` 같은 옛 이름이 남지만, 개명이 주는 기능적 이득이 없다 |

## 아키텍처

### 캘린더 연동 계층 (신규 · `data/calendar/`)

```
interface CalendarRepository {
    fun eventsOn(date: LocalDate): Flow<List<CalendarEvent>>
    suspend fun writableCalendars(): List<CalendarAccount>
    suspend fun addEvent(title: String, startMs: Long, endMs: Long, calendarId: Long): Long?
    fun openInSystemCalendar(eventId: Long)
    fun daysWithEvents(month: YearMonth): Flow<Set<LocalDate>>   // 미니 달력의 점
}
```

**`CalendarContract.Instances`만 쓴다.** `Events`는 "매주 화요일" 같은 규칙 원본을 주고,
`Instances`는 그 규칙을 이미 회차별로 펼쳐서 준다. 우리는 항상 날짜 구간 단위로 물어보므로
RRULE·예외·타임존·DST를 우리가 해석할 일이 없다. 캘린더를 직접 구현하는 것보다 연동이
쉬운 이유가 전부 여기에 있다.

`CalendarEvent`는 `id · title · startMs · endMs · isAllDay · color`만 담는다.
참석자·알림·설명·위치는 다루지 않으므로 쿼리하지 않는다.

**갱신**: `CalendarContract.CONTENT_URI`에 `ContentObserver`를 걸고 Flow로 흘린다.
삼성 캘린더에서 고치면 우리 화면이 따라온다. **캐시하지 않는다** — 진실의 원본은
시스템 캘린더 하나뿐이라 어긋날 여지가 구조적으로 없다.

**테스트 이음매**: 실제 구현(`ContentResolverCalendarRepository`)은 인터페이스 뒤에 둔다.
Today 화면 조립은 가짜 구현으로 검증한다.

### 할일 (기존 확장 · `PlannedFocusEntity`)

필드 두 개를 추가한다.

```kotlin
val dueDateEpochDay: Long,      // 어느 날의 할일인가 (생성 시점의 보고 있던 날짜)
val doneAtEpoch: Long? = null,  // 완료 표시. 타이머 없이 체크만 하는 경우도 있다
```

- **`dueDateEpochDay`는 non-null이다.** 모든 할일은 어느 하루에 속한다. "언젠가" 서랍은
  v1에 넣지 않는다 — 오늘 한 장이라는 컨셉이 흐려지고, 지금 앱에도 없던 개념이다.
- **반복 할일(`isRepeating`)은 `dueDateEpochDay`를 무시하고 항상 오늘 나타난다.**
  완료 여부는 `doneAtEpoch`가 오늘인지로 판정하므로 자정에 저절로 리셋된다.
- **미완료 이월은 DB를 고치지 않고 읽는 시점에 계산한다.** 오늘 목록 = `dueDate == 오늘`
  ∪ (`dueDate < 오늘` ∧ `doneAtEpoch == null`). 이월된 항목에는 `오늘 - dueDate`로
  "3일째" 배지를 붙인다. 백그라운드 작업도, 자정 알람도 필요 없고, 계속 밀리는 할일을
  조용히 숨기지도 않는다.

**마이그레이션**: 패키지명이 바뀌면 기기 입장에서 새 앱이라 기존 DB가 없다. 버전을 올리고
`fallbackToDestructiveMigration`으로 둔다. 출시 전이므로 보존할 사용자 데이터가 없다.

### 화면 구성

```
Today  ─┬─ 탭 ─→ Timer ─→ (완주) ─→ Today + 완주 시트
        ├─ Quick Start ─→ Timer
        ├─ 미니 달력 (날짜 점프)
        ├─ History ─→ Detail
        └─ Settings ─→ Stats / TaskStats
```

기존 `Routes`에서 `SESSION_COMPLETE`와 `UP_NEXT`가 사라지고, `BREAK`는 남는다.

## 화면 상세

### Today — 오늘 한 장

```
  ← 9월 2일 화 →              날짜 탭 → 미니 달력으로 점프
  ─────────────────────────
  종일   추석 연휴
   09:00  팀 회의        ●     캘린더 색 점 · 탭하면 60분 타이머
   11:30  ─── 지금 ───         현재 시각 선
   15:00  치과           ●
  ─────────────────────────
  할 일
   ▷ 논문 읽기      50분
   ▷ 운동           30분  3일째
   ▷ 장보기         20분
                          ＋
```

- **일정 땅금**: 그 날 일정만 시간순. 종일 일정은 맨 위 별도 줄. 지난 일정은 흐리게.
  오늘을 보고 있을 때만 현재 시각 선을 그린다.
- **일정 탭 → 타이머**. 지난 일정도 탭할 수 있다(흐리게 보일 뿐 잠기지 않는다) — 규칙이
  하나여야 익히기 쉽고, 늦게 시작하는 일이 실제로 흔하다.
  라벨은 일정 제목, 길이는 일정 길이. 종일 일정은 길이가 없으므로
  설정의 기본 시간을 쓴다. 일정으로 시작한 세션도 라벨 기준으로 통계에 쌓인다.
- **일정 행 오른쪽 아이콘 → 삼성 캘린더에서 열기** (`ACTION_VIEW` + `Events` URI).
- **할일 목록**: 지금의 `TodoScreen` 그대로. 탭하면 타이머, 스와이프 동작도 유지.
- **`＋`**: 시트 하나로 "할 일 추가 / 일정 추가" 두 갈래. 일정 추가는 제목·시작·길이
  세 칸이고, 쓸 캘린더는 설정에서 고른 기본 캘린더를 쓴다.
- **좌우 스와이프**로 어제·내일. 날짜 헤더 탭 → 월간 미니 달력(일정 있는 날에 점).

### 완주 시트 — 세 화면을 하나로

세션은 **시트가 뜨기 전에 이미 저장돼 있다.** 시트를 그냥 내려도 기록은 남는다.

```
  논문 읽기 · 50분 완료
  [메모]  [사진]
  [5분 쉬기]  [다음: 운동 ▷]
```

- 메모·사진은 기존 `PublishViewModel`의 저장 경로를 재사용하되, 저장된 세션을 **수정**한다
  (새로 만들지 않는다). 사진은 지금처럼 시스템 포토 피커 → 앱 전용 저장소 복사.
- "다음"은 오늘 남은 할일 중 첫 번째. 없으면 버튼이 없다.
- "쉬기"는 기존 `BreakScreen`으로 간다. **휴식이 끝나면 Today로 돌아온다** — 다음 할일을
  자동으로 시작하지 않는다. `NextUp`이 사라지면서 "휴식 뒤 이어서 무엇을 시작할지"를
  들고 다닐 이유가 없어졌으므로, `Routes.BREAK`의 `task`/`minutes` 인자도 함께 없앤다.
- 설정에서 캘린더 기록이 켜져 있으면, 저장하는 그 순간 기본 캘린더에 블록을 하나 만든다.

**자동 저장의 멱등성**: 타이머가 `COMPLETED`가 되는 순간 앱 스코프의 기록자가 저장한다.
앱이 죽은 사이 완주한 경우 재실행 시 `restore()`가 다시 `COMPLETED`를 내놓으므로, 저장과
`reset()` 사이에서 죽으면 두 번 저장될 수 있다. `ReceiptEntity`에 `startedAtEpoch`를 두고
같은 세션이 이미 기록됐는지 확인해서 막는다. DI가 이미 `fallbackToDestructiveMigration`이라
컬럼 추가에 마이그레이션 코드가 필요 없다.

### 설정

추가: **캘린더 연결 상태**, **일정을 쓸 기본 캘린더**, **집중 기록을 캘린더에 남기기(기본 꺼짐)**.
삭제: **사진 비율**, **영수증 길이**.

## 권한

**첫 실행 때 묻지 않는다.** 앱을 열자마자 뜨는 권한 팝업은 반사적으로 거부당하고,
한 번 거부되면 되돌리기가 훨씬 어렵다.

Today 맨 위에 "캘린더 연결하기" 줄이 얇게 있고, **그걸 탭했을 때** `READ_CALENDAR` ·
`WRITE_CALENDAR`를 요청한다. 사용자가 무엇을 얻는지 아는 상태에서 묻는다.

| 상태 | 동작 |
|---|---|
| 권한 없음 | 할일 + 타이머 앱으로 정상 동작. "캘린더 연결하기" 줄이 남는다 |
| 영구 거부 | 같은 줄이 시스템 설정으로 보내는 안내로 바뀐다 |
| 쓰기 가능한 캘린더 0개 | "일정 추가"가 비활성. 안내 문구 한 줄 |
| 권한을 나중에 회수당함 | `SecurityException`을 잡아 권한 없음 상태로 되돌린다 |

## 검증

- **`CalendarRepository` 가짜 구현**으로 Today 조립 테스트: 일정 0개, 종일 일정,
  겹치는 일정, 자정을 걸친 일정, 권한 없음.
- **순수 함수 단위 테스트**: 이월 판정과 "N일째" 계산, 반복 할일의 오늘 완료 판정,
  일정+할일을 한 목록으로 합치는 정렬.
- **`Instances` 쿼리는 계측 테스트**로 확인한다. 테스트 캘린더에 반복 일정을 하나 넣고
  회차가 제대로 펼쳐지는지 본다. 여기가 유일하게 안드로이드 실물이 필요한 지점이다.
- **현재 이 저장소에는 테스트가 하나도 없다** (`app/src/test/`, `app/src/androidTest/` 모두 없음).
  테스트 소스 세트를 만들고 Robolectric과 coroutines-test를 붙이는 것이 첫 작업이 된다.
  타이머 엔진은 이번 작업에서 건드리지 않으므로 소급해서 테스트를 붙이지는 않는다.
